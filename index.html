AMLCareBackendFrontend

Sanctions and PEP screening, end to end

Existing customers got screening data without re-entry, and auditors can tell automated changes from human ones.

Problem

Firms must screen clients, and the people who own them, for sanctions and political exposure. The data came from an external AI screening service with strict rate limits, existing customers had nothing precomputed, and the audit log couldn't separate automated changes from people's edits.

What I did

AccountonBackend

AI tax analysis that can pause and recover

A failed analysis now resumes instead of starting over, and reviews can't land on the wrong financial year.

Problem

Accounton's personal income tax analysis runs in a separate Python service, and generation was all-or-nothing. Separately, a review could be saved against the wrong financial year if the year rolled over between reading and writing.

What I did

Built the NestJS module that orchestrates the Python service, with explicit paused and error states and accountant feedback on each proposal. For the race, I added the current financial year to the update filter, so a stale write matches nothing and is refused. Jest tests pin the filter and cover the race.

NestJS, MongoDB, Jest, Python service integration

Why a filter and not a transaction? A conditional single-document update is atomic in MongoDB. It's cheaper, and enough here.

Scheduled runs never act twice

Serverless functions keep no memory, and the scheduler retries or fires twice. Every engine run follows the same steps, so a retried or duplicate run can never repeat a trade or an alert:

  1. Take a lock in MongoDB, with an expiry
  2. Load the strategy's state and fetch market data
  3. Run the pure strategy function
  4. Write events, trades and new state in one transaction, with a version check
  5. Alert only for events this run inserted; unique dedupe keys block repeats
  6. Release the lock and write an audit record, even on failure

If MongoDB is unreachable, the endpoint returns 503 so the scheduler retries. A candle is never silently skipped.

A data layer over four unreliable sources

Every outside fetch is cached in memory and in Redis, retried with backoff, and behind a circuit breaker: three failures pause the source for a minute and serve the last good copy. Source health shows in the app and triggers an alert if a source stays down for 15 minutes during market hours. Trading decisions refuse to say "trade now" on quotes older than three minutes.

₹0 on free tiers

The free scheduler allows ten schedules, and the overnight strategy needed nine job times. One schedule fires at many minutes and dispatches by IST time: 63 calls a day from one slot.

The options maths is written from scratch, not pulled from a library:

  • Black-76 pricing on the expiry's forward, with per-strike implied volatility
  • Option Greeks per lot, and an implied-volatility solver
  • A seeded 20,000-path Monte Carlo of target-before-stop, plus lognormal probability of profit
  • Payoff charts at expiry, T+0 and T+1, and a price-by-days scenario grid

Every trade is priced with a statutory cost model, with each charge a named constant:

  • Brokerage
  • STT
  • Exchange charges
  • SEBI fee
  • Stamp duty
  • GST
  • Slippage

When NSE blocks the option-chain request, legs fall back to Black-76 estimates from the index and India VIX, clearly marked as estimates.

Rules were chosen on one period of NSE data and checked on a later period they had never seen (credit spread: rules from Jul 2024 to Aug 2025, tested on Sep 2025 to Oct 2026). Where a strategy loses money, the app says so.

Most "strategy bugs" turned out to be data bugs. Each finding below changed results:

  • Fake trade signals. The free hourly feed had one-tick 15:30 stub bars that created phantom setups, fully empty candles that turned moving averages into NaN, and still-forming candles that made live results drift from backtests. All three are now cleaned before any rule reads the data.
  • A wrong daily move. The feed's previous-close field reported −3.8% on a day the real move was +0.3%.
  • A moving lot size. The Nifty lot size changed twice in two years (25, then 75, then 65). The app reads it live from NSE, along with expiry dates, because a hard-coded value would misstate risk by tens of percent.
  • Unadjusted history. NSE's daily bhavcopy files don't adjust the previous close for splits and bonuses, so I added a corporate-actions adjustment layer.

Checkout, from click to invoice

  1. Reserve the piece with an atomic conditional update. Every item is one of a kind, so two shoppers buying it at the same moment get exactly one winner; the other gets 409 STOCK_TAKEN.
  2. Create the order, invoice number and coupon redemption inside one MongoDB transaction. They all commit together or not at all.
  3. Create a Stripe PaymentIntent. Card data stays in Stripe's iframes and never touches the app's code.
  4. Signed, idempotent webhooks mark the order paid, failed or cancelled. Unpaid orders release their stock after 30 minutes.
  5. On payment, a PDFKit VAT invoice is numbered atomically, frozen, emailed and made downloadable to its owner only.

Money that can't drift

All prices are stored as integer fils (1 AED = 100 fils) and formatted only in the view, so floating-point rounding can't creep in. Orders snapshot their prices, so later catalogue changes never alter past orders.

A cart that doesn't trust the browser

The browser keeps only product IDs and quantities. A stateless endpoint prices the basket on the server, so guests and signed-in shoppers share one cart response, and a guest cart merges into the account on login.

Staff access

  • Invitation-only onboarding with one-time codes: hashed with a server secret, checked in constant time, five attempts, ten-minute expiry
  • Role checks re-read the role from the database instead of trusting the token
  • TOTP two-factor authentication: secrets encrypted with AES-256-GCM, no replay within a time window, hashed backup codes
  • JWT access tokens with rotating refresh tokens, helmet, rate limiting, and NoSQL-injection and XSS sanitising

An audit before launch

I ran a security audit with a threat model and endpoint inventory. It probed 123 routes with 7 forged-token variants, 861 requests in all, and found no authentication bypasses.

It did confirm one critical issue: a Stripe test payment could fulfil a real order. The testing I built caught it before launch. Testing also found and fixed password-spraying across accounts, an XSS-carrying email address at registration, and discounted prices ignored by sorting and filters.

Tests against a real database

About 240 Jest and Supertest integration tests run against an in-memory MongoDB replica set, not a mocked driver, because transactions behave differently on a standalone database. 184 Playwright tests cover API contracts, authorisation and injection, UI flows, responsive layouts and accessibility, and run nightly in GitHub Actions against an isolated database.

A custom linter fails CI on hard-coded colours; moving to semantic design tokens removed 779 of them.
